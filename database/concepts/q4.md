# Question 4

What is your strategy for optimizing PostgreSQL query execution plans when the query planner consistently chooses nested loops over hash joins for large dataset aggregations?

## Summary
When PostgreSQL keeps choosing nested loops for large joins, the query can become very slow. The fix is usually to help the planner by improving statistics, raising memory limits, and making sure the join conditions are indexed and selective.

## Problem
Nested loops are fine for small sets, but they are very slow when one table is large and the other is also large. If the planner uses a nested loop and the inner table must be scanned many times, the query can take much longer than a hash join would.

## Solution
- Run `ANALYZE` on the tables and indexes so the planner has accurate row counts.
- Increase `work_mem` so PostgreSQL can build hash tables in memory instead of spilling to disk.
- Add or improve indexes on the join keys and filter columns.
- Simplify the query and reduce the number of rows before the join by filtering early.
- If needed, temporarily disable nested loops with `SET enable_nestloop = off;` to test whether a hash join is faster.

## Key Concepts
- **Nested loop join:** good for small or very selective row sets, but can be slow for large data.
- **Hash join:** usually faster for large joins when there is enough memory to build the hash table.
- **Planner statistics:** PostgreSQL uses table and index statistics to choose a join type.
- **`work_mem`:** memory available for sorting and hashing. If too low, hash joins can spill to disk.
- **Filter pushdown:** apply filters before the join so the planner works on smaller sets.

## Example
```sql
EXPLAIN ANALYZE
SELECT c.customer_id,
       SUM(o.amount) AS total
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
WHERE c.active = true
  AND o.order_date >= '2026-01-01'
GROUP BY c.customer_id;
```
If this query uses nested loops and is slow:
- run `ANALYZE customers; ANALYZE orders;`
- increase `work_mem` for this session:
  `SET work_mem = '128MB';`
- make sure `orders.customer_id` is indexed.
- test with `SET enable_nestloop = off;` and compare `EXPLAIN ANALYZE`.

## Trade-offs
- **Higher `work_mem`:** helps hash joins, but too much memory per session can reduce overall concurrency.
- **Disabling nested loops:** useful for testing, but not a permanent fix.
- **Additional indexes:** speed up joins and filters, but slow down writes and use more storage.
- **More statistics:** make planner better, but analyzing very large tables also takes time.

# Question 1

How do you design a PostgreSQL schema to efficiently handle high-frequency, multi-tenant financial transaction inserts without severe lock contention?

## Summary
For busy financial transaction tables, keep inserts simple and avoid shared contention. Use partitioning, small indexes, and split tenant data so writes stay fast and locks stay short.

## What matters most
If rows are inserted thousands of times per second, the database needs to do as little work as possible for each insert.

- **Keep writes simple:** insert rows once, and avoid updating them later.
- **Separate tenants:** keep data for different customers isolated so one tenant does not slow down another.
- **Avoid big indexes:** every index slows down inserts, so only add indexes that are really needed.
- **Use partitioning:** split the data by time and/or tenant so the database can work on smaller pieces.

## How to design the schema
1. Create a main transaction table for append-only inserts.
2. Partition it by date, and if needed by tenant group.
3. Use a simple numeric primary key like `BIGSERIAL`.
4. Add only the smallest indexes needed for your common queries.
5. Put tenant metadata in separate tables, not in the main transaction row.

## Simple example
```sql
CREATE TABLE transaction_events (
  transaction_id BIGSERIAL PRIMARY KEY,
  tenant_id UUID NOT NULL,
  account_id UUID NOT NULL,
  amount NUMERIC(18,4) NOT NULL,
  currency CHAR(3) NOT NULL,
  transaction_ts TIMESTAMPTZ NOT NULL DEFAULT now(),
  transaction_type TEXT NOT NULL,
  metadata JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
) PARTITION BY RANGE (transaction_ts);

CREATE TABLE transaction_events_2026_07 PARTITION OF transaction_events
  FOR VALUES FROM ('2026-07-01') TO ('2026-08-01');

CREATE TABLE transaction_events_2026_08 PARTITION OF transaction_events
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

CREATE INDEX ON transaction_events (tenant_id, transaction_ts);
CREATE INDEX ON transaction_events (account_id, transaction_ts);
CREATE INDEX ON transaction_events (transaction_ts) USING BRIN;
```

## Why this helps
- `BIGSERIAL` keeps new inserts going into one place instead of scattering them around the table.
- Partitioning keeps recent data in a smaller area, making inserts and cleanup easier.
- A BRIN index on the timestamp is cheap and helps queries that look at recent time ranges.
- Only indexing frequent search keys reduces the overhead on every insert.

## Trade-offs
- **Good:**
  - Faster inserts.
  - Less lock contention between tenants.
  - Easier cleanup of old data.
- **Not so good:**
  - More work to manage partitions.
  - Queries across partitions can be harder.
  - You need to choose indexes carefully.
